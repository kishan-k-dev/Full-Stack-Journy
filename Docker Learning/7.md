# 🐳 7. Docker Networking

Until now we learned:

```text
Dockerfile
    ↓
Image
    ↓
Container
    ↓
Ports + Volumes + Environment Variables
```

But real applications usually have multiple services.

For example:

```text
                Browser
                   |
                   ↓
            FastAPI Container
                   |
                   ↓
             MySQL Container
```

How does the FastAPI container find the MySQL container?

How do containers communicate with each other?

How does a container access the internet?

That's where **Docker Networking** comes in.

---

# 1. What is Docker Networking?

Docker networking allows containers to communicate:

- With other containers
- With the host machine
- With external services
- With the internet

Simple idea:

```text
Container A
     |
     | Docker Network
     |
Container B
```

For example:

```text
FastAPI
   |
   | network
   ↓
MySQL
```

Docker provides networking automatically when containers are created.

---

# 2. Why Do We Need Docker Networks?

Imagine we have:

```text
Frontend
Backend
Database
Redis
```

Each one is running in its own container:

```text
┌───────────────┐
│ Frontend      │
│ Container     │
└───────┬───────┘
        |
        ↓
┌───────────────┐
│ Backend       │
│ Container     │
└───────┬───────┘
        |
        ↓
┌───────────────┐
│ MySQL         │
│ Container     │
└───────────────┘
```

They need a way to communicate.

Docker networking provides that communication.

# 8. Why Create a Custom Network?

Suppose we have:

```text
FastAPI
MySQL
Redis
```

Instead of relying on the default bridge:

```text
Default bridge
      |
 ┌────┼────┐
 ↓    ↓    ↓
API   DB  Redis
```

we can create:

```text
my-app-network
      |
 ┌────┼────┐
 ↓    ↓    ↓
API   DB  Redis
```

This gives us a dedicated network for our application.

# 12. Container-to-Container Communication

This is one of the most important concepts.

Suppose:

```text
FastAPI container
       |
       ↓
MySQL container
```

Both are connected to:

```text
my-app-network
```

FastAPI needs to connect to MySQL.

Instead of using:

```text
localhost
```

you can use the MySQL container's name as the hostname.

For example:

```text
mysql
```

if the MySQL container is named:

```text
mysql
```

So your database configuration might be:

```text
DATABASE_HOST=mysql
DATABASE_PORT=3306
```

---

# 13. VERY IMPORTANT: localhost Inside a Container

This causes a LOT of confusion for beginners.

Suppose FastAPI is running inside:

```text
fastapi-container
```

and MySQL is running inside:

```text
mysql-container
```

If FastAPI uses:

```text
localhost
```

it means:

```text
FastAPI container itself
```

NOT:

```text
MySQL container
```

Remember:

```text
localhost
   ↓
Current container
```

So this is usually WRONG for container-to-container communication:

```text
DATABASE_HOST=localhost
```

Instead, use the database container/service hostname:

```text
DATABASE_HOST=mysql
```

when `mysql` is the container name or network alias.

---

# 14. Container Name as Hostname

On a user-defined Docker network, containers can communicate using container names.

Example:

```bash
docker network create my-network
```

Run MySQL:

```bash
docker run -d \
  --name mysql \
  --network my-network \
  mysql:8
```

Run another container:

```bash
docker run -it \
  --network my-network \
  alpine
```

The second container can use:

```text
mysql
```

as the hostname for the MySQL container.

Conceptually:

```text
alpine
  |
  | hostname = mysql
  ↓
Docker DNS
  |
  ↓
mysql container
```

Docker provides DNS-based name resolution on user-defined networks.

---

# 15. Docker DNS

DNS normally helps convert a name into an IP address.

For example:

```text
google.com
    ↓
IP address
```

Docker also provides DNS resolution for containers on user-defined networks.

For example:

```text
mysql
  ↓
MySQL container IP
```

This means you don't need to hardcode the container's IP address.

---

# 16. Why Not Use Container IP?

You might inspect a container and find:

```text
172.18.0.2
```

You could technically connect using that IP.

But this is not a good approach for normal application configuration.

Why?

Container IP addresses can change when containers are recreated.

For example:

```text
Old container
172.18.0.2

Container recreated

New container
172.18.0.5
```

If your application uses:

```text
172.18.0.2
```

it can break.

Using:

```text
mysql
```

is much better.

Docker resolves the name to the current container address.

# 19. Published Port vs Internal Network

This is very important.

Suppose:

```text
FastAPI → MySQL
```

Both are on:

```text
my-network
```

FastAPI can communicate with:

```text
mysql:3306
```

You don't necessarily need:

```bash
-p 3306:3306
```

for FastAPI to reach MySQL.

The `-p` option is primarily for making a container port available through the host.

# 35. Important Security Idea

You don't necessarily need to expose MySQL to your host.

Avoid doing this unless you actually need host access:

```bash
-p 3306:3306
```

Your FastAPI container can communicate with MySQL through the internal Docker network.

Architecture:

```text
Internet
   |
   ↓
FastAPI
   |
   ↓
Internal Docker Network
   |
   ↓
MySQL
```

This reduces unnecessary external exposure.

# 36. Network Isolation

Suppose we have:

```text
frontend-network
```

and:

```text
database-network
```

Containers connected to different isolated networks are not automatically able to communicate with each other.

This helps separate application components.

For example:

```text
frontend-network
      |
   Frontend

backend-network
      |
  FastAPI
      |
    MySQL
```

Only the services that need communication should be connected to the appropriate networks.

# 38. Network Drivers

You don't need to memorize every driver yet.

But know the basic idea:

| Driver | Simple Meaning |
|---|---|
| `bridge` | Containers communicate on same Docker host |
| `host` | Container uses host networking |
| `none` | No normal network connectivity |
| `overlay` | Network spanning multiple Docker hosts, commonly in Swarm |
| `ipvlan` | Container gets connectivity using IPvlan |
| `macvlan` | Container can appear as a network device |

For your current learning:

```text
Focus mainly on:
bridge
```

Later:

```text
Kubernetes Networking
```

will take this much further.

# 39. Host Network

With:

```bash
--network host
```

the container uses the host's network stack rather than the normal isolated bridge networking model.

Example:

```bash
docker run --network host nginx
```

This is different from:

```bash
docker run -p 8080:80 nginx
```

For normal beginner Docker applications, you will mostly use user-defined bridge networks.

---

# 40. None Network

The `none` network provides a highly isolated networking setup.

Example:

```bash
docker run --network none alpine
```

The container does not get normal network connectivity.

This can be useful for workloads that don't need networking.

# 41. Common Networking Mistakes

## Mistake 1 — Using localhost for another container

Wrong:

```text
DATABASE_HOST=localhost
```

when MySQL is in another container.

Usually correct:

```text
DATABASE_HOST=mysql
```

---

## Mistake 2 — Using container IP addresses everywhere

Avoid hardcoding:

```text
172.18.0.5
```

because the IP can change.

Prefer:

```text
mysql
```

on a user-defined network.

---

## Mistake 3 — Publishing every port

You don't need:

```text
-p
```

for every internal service.

For example:

```text
FastAPI → MySQL
```

can communicate through the Docker network without making MySQL publicly accessible through the host.

---

## Mistake 4 — Containers on different networks

Suppose:

```text
API → network-a
DB  → network-b
```

They won't automatically communicate just because both are Docker containers.

Connect them to a common network when communication is required.

---

## Mistake 5 — Forgetting --network

You create:

```bash
docker network create my-network
```

but then run:

```bash
docker run my-app
```

The container won't automatically join your custom network.

Use:

```bash
docker run --network my-network my-app
```

# 43. Port Mapping vs Networking

Don't confuse these.

### Port Mapping

Used mainly to make a container service accessible through the host.

```bash
-p 8000:8000
```

Example:

```text
Browser
   ↓
Host:8000
   ↓
Container:8000
```

### Docker Network

Used for communication between containers.

```text
FastAPI
   ↓
Docker Network
   ↓
MySQL
```

Memory trick:

```text
-p
↓
Host ↔ Container

Network
↓
Container ↔ Container
```

# 46. Interview Questions & Answers

## Q1. What is Docker networking?

**Answer:**

Docker networking allows containers to communicate with each other, the host, and external networks.

---

## Q2. What is the default Docker network?

**Answer:**

Docker creates a default bridge network called `bridge`. Containers run on this network when no other network is specified.

---

## Q3. What is a bridge network?

**Answer:**

A bridge network allows containers on the same Docker host to communicate while providing network isolation from containers on other networks.

---

## Q4. Why do we create custom Docker networks?

**Answer:**

Custom networks provide better isolation and allow containers on the same network to communicate using container names through Docker's DNS.

---

## Q5. How do you create a Docker network?

**Answer:**

```bash
docker network create my-network
```

---

## Q6. How do you connect a container to a network?

**Answer:**

When creating it:

```bash
docker run --network my-network my-app
```

Or for an existing container:

```bash
docker network connect my-network my-container
```

---

## Q7. How can two containers communicate?

**Answer:**

They can communicate when they are connected to the same Docker network. On a user-defined network, they can normally use container names as hostnames.

---

## Q8. Why should we use container names instead of container IPs?

**Answer:**

Container IP addresses can change when containers are recreated. Container names provide stable service discovery through Docker's DNS on user-defined networks.

---

## Q9. What does localhost mean inside a container?

**Answer:**

`localhost` refers to the container itself, not another container.

---

## Q10. How does FastAPI connect to MySQL in another container?

**Answer:**

If both containers are on the same user-defined network, FastAPI can connect using the MySQL container name as the hostname.

For example:

```text
Host: mysql
Port: 3306
```

---

## Q11. Do we need to publish MySQL's port for FastAPI to connect to it?

**Answer:**

No. If both containers are connected to the same Docker network, FastAPI can communicate with MySQL using the internal container port.

---

## Q12. What is the difference between `-p` and `--network`?

**Answer:**

`-p` publishes a container port through the Docker host, while `--network` connects the container to a Docker network for container-to-container communication.

---

## Q13. Can a container belong to multiple networks?

**Answer:**

Yes. A container can be connected to multiple Docker networks.

---

## Q14. What is Docker DNS?

**Answer:**

Docker provides DNS-based service discovery on user-defined networks, allowing containers to communicate using container names instead of hardcoded IP addresses.

---

## Q15. What network would you normally use for a simple multi-container application?

**Answer:**

A user-defined bridge network is a common choice for containers running on the same Docker host.

- `bridge` is the most important network type for your current Docker learning.
- Docker automatically provides a default `bridge` network.
- User-defined bridge networks are preferred for multi-container applications.
- Containers on the same user-defined network can communicate using container names.
- Docker provides DNS-based name resolution on user-defined networks.
- Don't hardcode container IP addresses in application configuration.
- `localhost` inside a container means that container itself.
- `-p` is mainly for publishing a container port through the host.
- Container-to-container communication can happen through a Docker network without publishing every internal service port.
- A container can connect to multiple networks.
- `docker network inspect` is extremely useful for troubleshooting.

The big picture is now:

```text
Dockerfile
     ↓
Image
     ↓
Container
     ↓
Ports
     ↓
Volumes
     ↓
Environment Variables
     ↓
Networking
     ↓
Multiple Containers
```
