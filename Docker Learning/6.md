# 🐳 6. Docker Ports, Volumes & Environment Variables

Until now we learned:

```text
Dockerfile
    ↓
Image
    ↓
Container
```

But a real application needs more than just a container.

For example:

```text
FastAPI Application
        ↓
Needs a port
        ↓
Needs database storage
        ↓
Needs configuration
        ↓
Needs passwords/API keys
```

Docker provides different mechanisms for these things.

In this topic we will learn:

- Docker ports
- Host port vs container port
- Port mapping
- Container storage
- Why container data can disappear
- Docker volumes
- Bind mounts
- Environment variables
- `.env` files

# 1. Docker Ports

Let's say we have a Flask application:

```python
app.run(host="0.0.0.0", port=8000)
```

The application is listening on:

```text
Port 8000
```

But the application is running inside a Docker container.

```text
Your Computer
      |
      |
      ↓
Docker Container
      |
      ↓
Python Application
      |
      ↓
Port 8000
```

How can we access it from our browser?

We use **port mapping**.

---

# 2. Host Port vs Container Port

This is very important.

Suppose we run:

```bash
docker run -p 5000:8000 my-app
```

The format is:

```text
-p HOST_PORT:CONTAINER_PORT
```

So:

```text
5000 → Host port
8000 → Container port
```

The flow becomes:

```text
Browser
   ↓
localhost:5000
   ↓
Host port 5000
   ↓
Docker
   ↓
Container port 8000
   ↓
Application
```

---

# 3. Simple Port Example

Suppose your application uses:

```text
Container port = 8000
```

You can map it to:

```text
Host port = 5000
```

using:

```bash
docker run -p 5000:8000 my-app
```

Now open:

```text
http://localhost:5000
```

Docker forwards the request to:

```text
Container:8000
```

---

# 4. Can Host and Container Ports Be Different?

Yes.

For example:

```bash
docker run -p 9000:8000 my-app
```

means:

```text
Host       Container
9000  →    8000
```

You access:

```text
localhost:9000
```

while the application inside the container still listens on:

```text
8000
```

---

# 5. Multiple Containers Can Use Different Host Ports

Suppose we have two applications.

Application 1:

```text
Container port = 8000
```

Application 2:

```text
Container port = 8000
```

Both can run because they can use different host ports.

Example:

```bash
docker run -d -p 5000:8000 app1
docker run -d -p 5001:8000 app2
```

Now:

```text
localhost:5000 → app1
localhost:5001 → app2
```

Inside both containers:

```text
8000
```

---

# 6. Port Mapping Diagram

Remember this:

```text
                 Docker Host
              Your Computer
                    |
                    |
             localhost:5000
                    |
                    ↓
          ┌──────────────────┐
          │ Docker Container │
          │                  │
          │   Port 8000      │
          │       ↓          │
          │ Python App       │
          └──────────────────┘
```

Command:

```bash
docker run -p 5000:8000 my-app
```

Memory trick:

```text
-p HOST:CONTAINER
```

# 7. EXPOSE vs -p

You learned `EXPOSE` in the previous topic.

Example:

```dockerfile
EXPOSE 8000
```

This indicates that the application is intended to use port 8000 inside the container.

But it doesn't publish that port to your host.

To actually publish it:

```bash
docker run -p 8000:8000 my-app
```

So:

```text
EXPOSE
   ↓
Documents/intends container port

-p
   ↓
Publishes/maps container port to host
```

---

# 8. What Happens Without -p?

Suppose you run:

```bash
docker run my-app
```

The application may be running inside the container.

But you may not be able to access it through:

```text
localhost:8000
```

from your host.

Why?

Because you didn't publish the container port.

For example:

```text
Container
    ↓
Application
    ↓
Port 8000
    ↓
Not mapped to host
```

# 9. Docker Container Storage

Now let's talk about data.

Suppose our application creates:

```text
user_data.txt
```

inside the container.

The file exists:

```text
Container
└── /app
    └── user_data.txt
```

But containers are designed to be replaceable.

If the container is removed:

```bash
docker rm my-container
```

the data stored only inside that container is also removed.

This is why persistent storage is important.

---

# 10. Why Do We Need Persistent Storage?

Imagine a MySQL database running inside a container.

```text
MySQL Container
      ↓
Customer Data
      ↓
Orders
      ↓
Users
```

If the container is deleted and the database data only existed inside the container:

```text
Container deleted
       ↓
Data can be lost
```

We don't want that.

Instead:

```text
Container
    ↓
Database
    ↓
Docker Volume
    ↓
Persistent data
```

---

# 11. What is a Docker Volume?

A Docker volume is storage managed by Docker that can be attached to containers.

Example:

```bash
docker volume create my-volume
```

Check volumes:

```bash
docker volume ls
```

You may see:

```text
DRIVER    VOLUME NAME
local     my-volume
```

---

# 12. Using a Volume

Example:

```bash
docker run -d \
  --name my-container \
  --mount source=my-volume,target=/data \
  alpine
```

Now:

```text
Docker Volume
     ↓
/data inside container
```

Anything written to `/data` is stored in the volume.

---

# 13. Volume Diagram

```text
                 Docker
                   |
          ┌────────┴────────┐
          ↓                 ↓
     Container          Volume
          |                 |
       /data  ──────────────┘
          |
       Files
```

The important idea:

```text
Container = Application

Volume = Persistent data
```

---

# 14. Volume Example

Create a volume:

```bash
docker volume create app-data
```

Run a container:

```bash
docker run -it \
  --name data-container \
  --mount source=app-data,target=/data \
  alpine sh
```

Inside the container:

```bash
echo "Hello Docker" > /data/message.txt
```

Exit:

```bash
exit
```

Now remove the container:

```bash
docker rm data-container
```

Create another container using the same volume:

```bash
docker run -it \
  --mount source=app-data,target=/data \
  alpine sh
```

Check:

```bash
cat /data/message.txt
```

You should still get:

```text
Hello Docker
```

Why?

Because the data was stored in:

```text
app-data
```

not only inside the previous container.

---

# 15. Useful Volume Commands

Create volume:

```bash
docker volume create my-volume
```

List volumes:

```bash
docker volume ls
```

Inspect volume:

```bash
docker volume inspect my-volume
```

Remove volume:

```bash
docker volume rm my-volume
```

Remove unused volumes:

```bash
docker volume prune
```

Be careful with:

```bash
docker volume prune
```

because it can remove unused volumes.

---

# 16. Volume Short Syntax

You may also see:

```bash
docker run -v my-volume:/data alpine
```

Meaning:

```text
my-volume → /data
```

So:

```bash
-v volume-name:container-path
```

Example:

```bash
docker run -v app-data:/data alpine
```

---

# 17. --mount vs -v

There are two common ways to mount storage.

### Short syntax

```bash
-v app-data:/data
```

### Explicit syntax

```bash
--mount source=app-data,target=/data
```

For learning, you should understand both.

Docker documentation generally recommends the more explicit `--mount` syntax because it makes the configuration clearer.

---

# 18. Docker Volume vs Container Storage

Without volume:

```text
Container
    ↓
Data
    ↓
Container removed
    ↓
Data removed
```

With volume:

```text
Container
    ↓
Data
    ↓
Volume
    ↓
Container removed
    ↓
Volume still exists
    ↓
Data remains
```

This is why volumes are commonly used for databases and other persistent data.

---

# 19. What is a Bind Mount?

A bind mount connects a specific directory or file from your computer to a path inside the container.

Example:

```bash
docker run \
  --mount type=bind,src=.,dst=/app \
  python:3.12
```

This means:

```text
Your computer
    .
    ↓
/app inside container
```

---

# 20. Bind Mount Diagram

```text
Your Computer
│
└── project/
      │
      ├── app.py
      └── requirements.txt
             |
             |
             ↓
       Docker Container
             |
           /app
             |
      ├── app.py
      └── requirements.txt
```

If you change `app.py` on your computer, the container sees the changed file through the mount.

This is very useful during development.

---

# 21. Volume vs Bind Mount

This is an important interview topic.

### Docker Volume

```text
Managed by Docker
```

Useful for:

```text
Database data
Persistent application data
Production storage
```

### Bind Mount

```text
Uses a specific path on your computer
```

Useful for:

```text
Development
Source code
Configuration files
Sharing files
```

Simple memory:

```text
Volume
↓
Docker-managed storage

Bind Mount
↓
Host folder ↔ Container folder
```

---

# 22. Bind Mount Example for Development

Suppose:

```text
my-project/
│
├── app.py
└── requirements.txt
```

You can mount the current directory:

```bash
docker run -it \
  --mount type=bind,src=.,dst=/app \
  python:3.12 bash
```

Inside the container:

```bash
cd /app
```

You can see:

```text
app.py
requirements.txt
```

The files are coming from your computer.

---

# 23. Read-Only Bind Mount

A bind mount can also be read-only.

Example:

```bash
docker run \
  --mount type=bind,src=.,dst=/app,readonly \
  my-app
```

Now the container can read the files but should not modify them through that mount.

This can be useful when you want to protect host files.

# 24. Environment Variables

Now let's move to configuration.

Suppose our Python application needs:

```text
DATABASE_HOST
DATABASE_PORT
DATABASE_NAME
```

Instead of hardcoding these values:

```python
database_host = "localhost"
```

we can use environment variables.

For example:

```text
DATABASE_HOST=mysql
DATABASE_PORT=3306
DATABASE_NAME=mydatabase
```

---

# 25. Why Use Environment Variables?

Because configuration can change between environments.

For example:

### Development

```text
DATABASE_HOST=localhost
```

### Docker

```text
DATABASE_HOST=mysql
```

### Production

```text
DATABASE_HOST=production-db.example.com
```

The application code can remain the same.

Only the configuration changes.

---

# 26. Setting Environment Variables with docker run

Use:

```bash
docker run -e APP_ENV=development my-app
```

Here:

```text
-e
↓
Set environment variable
```

Variable:

```text
APP_ENV
```

Value:

```text
development
```

---

# 27. Multiple Environment Variables

You can use multiple `-e` options.

Example:

```bash
docker run \
  -e APP_ENV=production \
  -e PORT=8000 \
  -e DEBUG=false \
  my-app
```

Now the container receives:

```text
APP_ENV=production
PORT=8000
DEBUG=false
```

---

# 28. Checking Environment Variables

You can use:

```bash
docker exec my-container env
```

This displays environment variables available inside the container.

You can also run:

```bash
docker exec my-container printenv
```

---

# 29. Python Example with Environment Variables

Python can read environment variables using:

```python
import os

app_env = os.getenv("APP_ENV")

print("Environment:", app_env)
```

Run:

```bash
docker run -e APP_ENV=production my-python-app
```

Output:

```text
Environment: production
```

# 30. Better Configuration Example

Suppose your application needs:

```text
DATABASE_HOST
DATABASE_USER
DATABASE_PASSWORD
DATABASE_NAME
```

Instead of:

```python
DATABASE_PASSWORD = "mypassword"
```

use:

```python
import os

DATABASE_HOST = os.getenv("DATABASE_HOST")
DATABASE_USER = os.getenv("DATABASE_USER")
DATABASE_PASSWORD = os.getenv("DATABASE_PASSWORD")
DATABASE_NAME = os.getenv("DATABASE_NAME")
```

Now Docker can provide the values.

---

# 31. The Problem with Many -e Options

Imagine your application needs:

```text
DATABASE_HOST
DATABASE_PORT
DATABASE_USER
DATABASE_PASSWORD
DATABASE_NAME
SECRET_KEY
JWT_SECRET
API_URL
DEBUG
```

Running this becomes ugly:

```bash
docker run \
  -e DATABASE_HOST=mysql \
  -e DATABASE_PORT=3306 \
  -e DATABASE_USER=admin \
  -e DATABASE_PASSWORD=password \
  -e DATABASE_NAME=mydb \
  -e SECRET_KEY=abc123 \
  -e JWT_SECRET=xyz456 \
  -e API_URL=http://localhost:8000 \
  -e DEBUG=false \
  my-app
```

There is a cleaner approach.

Use an `.env` file.

---

# 32. What is a .env File?

A `.env` file stores environment variable values in a simple format.

Example:

```text
APP_ENV=development
PORT=8000
DATABASE_HOST=mysql
DATABASE_PORT=3306
DATABASE_NAME=mydatabase
```

Project:

```text
my-app/
│
├── Dockerfile
├── app.py
├── requirements.txt
└── .env
```

---

# 33. Using .env with docker run

You can pass the file using:

```bash
docker run --env-file .env my-app
```

Docker loads the variables from the file into the container.

So instead of:

```bash
docker run -e APP_ENV=development -e PORT=8000 my-app
```

you can use:

```bash
docker run --env-file .env my-app
```

---

# 34. .env Example

Create:

```text
.env
```

Contents:

```text
APP_ENV=development
PORT=8000
DATABASE_HOST=mysql
DATABASE_PORT=3306
```

Run:

```bash
docker run --env-file .env my-app
```

Inside the container:

```text
APP_ENV=development
PORT=8000
DATABASE_HOST=mysql
DATABASE_PORT=3306
```

---

# 35. Important .env Security Rule

Do NOT blindly upload `.env` files containing secrets to GitHub.

For example:

```text
DATABASE_PASSWORD=supersecret
JWT_SECRET=my-secret-key
API_KEY=123456
```

These are sensitive.

Usually add:

```text
.env
```

to:

```text
.gitignore
```

Example:

```gitignore
.env
```

Then create a safe example file:

```text
.env.example
```

Example:

```text
APP_ENV=development
PORT=8000
DATABASE_HOST=mysql
DATABASE_PORT=3306
DATABASE_NAME=mydatabase
DATABASE_USER=your_username
DATABASE_PASSWORD=your_password
```

This shows other developers which variables they need without exposing your real secrets.

---

# 36. .env vs .env.example

### .env

Contains your actual local configuration.

```text
DATABASE_PASSWORD=real_password
```

Should generally not be committed.

### .env.example

Contains placeholder values.

```text
DATABASE_PASSWORD=your_password
```

Can be committed to GitHub.

Memory trick:

```text
.env
↓
Real values

.env.example
↓
Template
```

---

# 37. Environment Variables vs Dockerfile ENV

You can define an environment variable in Dockerfile:

```dockerfile
ENV APP_ENV=production
```

You can also override it when running the container:

```bash
docker run -e APP_ENV=development my-app
```

So the runtime configuration can change without rebuilding the image.

This is one reason environment variables are useful.

# 46. Common Mistakes

## Mistake 1 — Reversing -p

Wrong:

```bash
docker run -p 8000:5000 my-app
```

when your application listens on container port 8000.

Remember:

```text
-p HOST:CONTAINER
```

---

## Mistake 2 — Thinking EXPOSE publishes the port

This:

```dockerfile
EXPOSE 8000
```

doesn't replace:

```bash
-p 8000:8000
```

---

## Mistake 3 — Storing database data only inside container

For databases, persistent storage is important.

Instead of relying only on container filesystem:

```text
MySQL Container
       ↓
Volume
       ↓
Persistent data
```

---

## Mistake 4 — Putting secrets directly in Dockerfile

Avoid:

```dockerfile
ENV DATABASE_PASSWORD=secret123
```

Do not bake sensitive values into your image unnecessarily.

Use appropriate runtime configuration and, in production, dedicated secret-management mechanisms.

---

## Mistake 5 — Uploading .env to GitHub

Avoid committing:

```text
.env
```

when it contains real secrets.

Use:

```text
.env.example
```

for documentation.

---

## Mistake 6 — Using bind mounts without understanding permissions

A bind mount gives the container access to a host path.

For example:

```bash
--mount type=bind,src=.,dst=/app
```

The container can interact with that host directory.

Be careful with write access, especially when mounting sensitive host directories.

# 48. Interview Questions & Answers

## Q1. What is Docker port mapping?

**Answer:**

Port mapping connects a port on the Docker host to a port inside the container.

Example:

```bash
docker run -p 5000:8000 my-app
```

Here port 5000 on the host maps to port 8000 in the container.

---

## Q2. What is the syntax of -p?

**Answer:**

```text
-p HOST_PORT:CONTAINER_PORT
```

Example:

```bash
-p 5000:8000
```

---

## Q3. What is a Docker volume?

**Answer:**

A Docker volume is Docker-managed persistent storage that can be attached to containers.

It is commonly used for data that needs to survive container replacement, such as database data.

---

## Q4. Why do we use volumes?

**Answer:**

We use volumes to persist important data independently of a container's lifecycle.

---

## Q5. What is a bind mount?

**Answer:**

A bind mount maps a specific file or directory from the host machine into a container.

It is commonly useful during development for sharing source code.

---

## Q6. What is the difference between a volume and a bind mount?

**Answer:**

A volume is managed by Docker, while a bind mount uses a specific path from the host filesystem.

---

## Q7. What are environment variables?

**Answer:**

Environment variables are configuration values provided to an application at runtime.

Examples:

```text
DATABASE_HOST
DATABASE_PORT
APP_ENV
DEBUG
```

---

## Q8. How do you pass an environment variable to a container?

**Answer:**

Using `-e`.

Example:

```bash
docker run -e APP_ENV=production my-app
```

---

## Q9. How do you pass multiple environment variables?

**Answer:**

Use multiple `-e` options or an environment file.

Example:

```bash
docker run \
  -e APP_ENV=production \
  -e PORT=8000 \
  my-app
```

---

## Q10. What is an .env file?

**Answer:**

An `.env` file is a convenient way to store configuration values as key-value pairs and load them into an application or container.

---

## Q11. How do you use an .env file with docker run?

**Answer:**

Use:

```bash
docker run --env-file .env my-app
```

---

## Q12. Should we commit .env to GitHub?

**Answer:**

Normally, no, especially if it contains secrets such as passwords or API keys.

I would add `.env` to `.gitignore` and provide a `.env.example` file with placeholder values.

---

## Q13. What is the difference between EXPOSE and -p?

**Answer:**

`EXPOSE` documents the intended container port, while `-p` publishes/maps a container port to a host port.

---

## Q14. Why is persistent storage important for databases?

**Answer:**

Because database data should survive container replacement. Docker volumes provide storage that exists independently of an individual container.

---

## Q15. Why would you use a bind mount?

**Answer:**

I would commonly use a bind mount during development when I want the container to access source code or configuration files directly from my host machine.
