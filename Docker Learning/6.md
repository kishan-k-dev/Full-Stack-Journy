# 🐳 5. Dockerfile

A Dockerfile is one of the most important concepts in Docker.

Until now, we were mainly using existing images like:

```bash
docker pull nginx
docker run nginx
```

But what if we have our own application?

For example:

```text
My Python Application
        ↓
    app.py
    requirements.txt
        ↓
   I want to run this
   inside a container
```

Docker needs instructions to know:

- Which base environment to use
- Where to put the application
- Which files to copy
- Which dependencies to install
- Which command to run

That is exactly what a **Dockerfile** does.

---

# 1. What is a Dockerfile?

A **Dockerfile** is a text file containing instructions that Docker uses to build a Docker image.

Example:

```dockerfile
FROM python:3.12

WORKDIR /app

COPY requirements.txt .

RUN pip install -r requirements.txt

COPY . .

CMD ["python", "app.py"]
```

Docker reads these instructions from top to bottom and creates an image.

Simple idea:

```text
Dockerfile
     ↓
docker build
     ↓
Docker Image
     ↓
docker run
     ↓
Container
```

So remember:

```text
Dockerfile → Image → Container
```

---

# 2. Why Do We Need a Dockerfile?

Imagine you have a Python application.

Normally you might need to manually do:

```bash
Install Python
Install dependencies
Create application folder
Copy application files
Run application
```

If another developer gets your project, they may have to repeat everything.

Dockerfile solves this problem.

You write the instructions once:

```dockerfile
FROM python:3.12

WORKDIR /app

COPY requirements.txt .

RUN pip install -r requirements.txt

COPY . .

CMD ["python", "app.py"]
```

Now anyone can build the same image using:

```bash
docker build -t my-python-app .
```

This makes the application environment much more consistent.

---

# 3. Dockerfile vs Image vs Container

This is VERY important.

### Dockerfile

Instructions for creating an image.

```text
Dockerfile
    ↓
"Here is how my application should be packaged"
```

### Image

The packaged application environment.

```text
Image
    ↓
"Here is everything needed to run my application"
```

### Container

A running instance of that image.

```text
Container
    ↓
"My application is actually running"
```

Easy example:

```text
Dockerfile = Recipe
Image      = Prepared food
Container  = Food being served
```

# 4. Basic Dockerfile Structure

A simple Dockerfile can look like this:

```dockerfile
FROM python:3.12

WORKDIR /app

COPY . .

RUN pip install -r requirements.txt

EXPOSE 8000

ENV APP_ENV=production

CMD ["python", "app.py"]
```

Let's understand each instruction.

```text
FROM
  ↓
WORKDIR
  ↓
COPY
  ↓
RUN
  ↓
EXPOSE
  ↓
ENV
  ↓
CMD
```

Not every Dockerfile must contain exactly these instructions, but these are some of the most common ones.

---

# 5. FROM

## What is FROM?

`FROM` specifies the base image for our Docker image.

Example:

```dockerfile
FROM python:3.12
```

This means:

> Start my image using the Python 3.12 image.

Instead of installing Python manually, Docker starts with an image that already contains Python.

---

## Example

For a Python application:

```dockerfile
FROM python:3.12
```

For an Nginx application:

```dockerfile
FROM nginx
```

For Ubuntu:

```dockerfile
FROM ubuntu
```

For Node.js:

```dockerfile
FROM node:22
```

---

## Why is FROM important?

Because our application needs some base environment.

For example:

```text
Python application
       ↓
Needs Python
       ↓
FROM python:3.12
```

---

# 6. WORKDIR

## What is WORKDIR?

`WORKDIR` sets the working directory inside the image.

Example:

```dockerfile
WORKDIR /app
```

Now Docker will work inside:

```text
/app
```

for following instructions.

---

## Example

```dockerfile
FROM python:3.12

WORKDIR /app
```

Think of it like:

```text
Container filesystem

/
├── bin
├── usr
├── etc
└── app
    └── ← Our application lives here
```

---

## Why use WORKDIR?

Without a proper working directory, files and commands can end up in unexpected locations.

So a good practice is:

```dockerfile
WORKDIR /app
```

---

# 7. COPY

## What is COPY?

`COPY` copies files from our computer into the Docker image.

Example:

```dockerfile
COPY app.py .
```

If our computer contains:

```text
project/
│
├── Dockerfile
└── app.py
```

Then after:

```dockerfile
WORKDIR /app

COPY app.py .
```

the image contains:

```text
/app
└── app.py
```

---

## Copy the entire project

We can also write:

```dockerfile
COPY . .
```

This means:

```text
First . = current project directory

Second . = current WORKDIR
```

So:

```dockerfile
WORKDIR /app
COPY . .
```

means:

```text
Your project files
       ↓
     /app
```

---

# 8. RUN

## What is RUN?

`RUN` executes a command while the Docker image is being built.

Example:

```dockerfile
RUN pip install -r requirements.txt
```

This installs Python dependencies into the image.

Another example:

```dockerfile
RUN apt-get update
```

Another:

```dockerfile
RUN mkdir /app/data
```

---

# 9. RUN vs CMD

🔥 VERY IMPORTANT INTERVIEW QUESTION.

Many beginners confuse these two.

## RUN

`RUN` executes during **image building**.

Example:

```dockerfile
RUN pip install flask
```

This happens when:

```bash
docker build
```

is executed.

---

## CMD

`CMD` specifies the default command that runs when a container starts.

Example:

```dockerfile
CMD ["python", "app.py"]
```

This happens when:

```bash
docker run
```

starts the container.

---

## Easy Memory Trick

```text
RUN → Build time

CMD → Container runtime
```

Or:

```text
docker build
     ↓
    RUN
     ↓
  Image
     ↓
docker run
     ↓
    CMD
     ↓
 Application starts
```

---

# 10. CMD

## What is CMD?

`CMD` defines the default command to execute when a container starts.

Example:

```dockerfile
CMD ["python", "app.py"]
```

When we run:

```bash
docker run my-python-app
```

Docker starts:

```bash
python app.py
```

---

## Another Example

```dockerfile
CMD ["nginx", "-g", "daemon off;"]
```

The exact command depends on the application.

---

## Important

A Dockerfile normally has one effective `CMD`.

If multiple `CMD` instructions are present, only the last one takes effect.

---

# 11. EXPOSE

## What is EXPOSE?

`EXPOSE` tells Docker/documentation which port the application is intended to listen on.

Example:

```dockerfile
EXPOSE 8000
```

This means:

```text
Application
    ↓
Listening on port 8000
```

For a Flask/FastAPI application commonly:

```dockerfile
EXPOSE 8000
```

---

# 12. EXPOSE Does NOT Publish the Port

🔥 Important.

This:

```dockerfile
EXPOSE 8000
```

does NOT automatically make the application accessible from your computer.

You still need port mapping when running the container.

Example:

```bash
docker run -p 8000:8000 my-python-app
```

Remember:

```text
EXPOSE
   ↓
Documents/intends the container port

-p
   ↓
Actually maps/publishes the port
```

Example:

```text
Your computer
localhost:8000
      ↓
      ↓
Container:8000
      ↓
Python application
```

---

# 13. ENV

## What is ENV?

`ENV` sets an environment variable inside the image/container.

Example:

```dockerfile
ENV APP_ENV=production
```

Now the application can access:

```text
APP_ENV=production
```

---

## Another Example

```dockerfile
ENV PORT=8000
```

Then the application can use the `PORT` environment variable.

---

## Why use ENV?

Environment variables are useful for configuration.

For example:

```text
APP_ENV
PORT
DATABASE_HOST
DATABASE_NAME
```

However, do NOT put sensitive secrets directly into a Dockerfile.

Avoid:

```dockerfile
ENV DB_PASSWORD=mysecretpassword
```

Secrets should be handled more securely.

We will learn better approaches later.

# 20. Why COPY requirements.txt First?

Notice this:

```dockerfile
COPY requirements.txt .

RUN pip install -r requirements.txt

COPY . .
```

Instead of simply:

```dockerfile
COPY . .

RUN pip install -r requirements.txt
```

Why?

Docker builds images in layers and can reuse cached build steps when inputs haven't changed.

If your application source changes frequently but `requirements.txt` hasn't changed, separating these steps can help Docker reuse the dependency-installation layer.

This becomes especially useful as projects get larger.

# 25. Common Mistakes

## Mistake 1 — Confusing RUN and CMD

Wrong understanding:

```text
RUN = start application
```

Correct:

```text
RUN = execute during image build
CMD = default command when container starts
```

---

## Mistake 2 — Thinking EXPOSE publishes the port

This:

```dockerfile
EXPOSE 8000
```

does not replace:

```bash
docker run -p 8000:8000 my-app
```

---

## Mistake 3 — Wrong application host

For a web application running inside Docker, the application often needs to listen on:

```text
0.0.0.0
```

rather than only:

```text
127.0.0.1
```

For example:

```python
app.run(host="0.0.0.0", port=8000)
```

This allows the application to accept connections through the container's network interface.

---

## Mistake 4 — Forgetting requirements.txt

If your application uses Flask:

```python
from flask import Flask
```

you need Flask installed in the image.

For example:

```text
requirements.txt
```

contains:

```text
flask
```

and Dockerfile contains:

```dockerfile
RUN pip install -r requirements.txt
```

---

## Mistake 5 — Wrong COPY path

For example:

```dockerfile
WORKDIR /app

COPY app.py .
```

means:

```text
app.py → /app/app.py
```

Always understand where your files are going.

Whenever you see a Dockerfile, think:

```text
1. FROM
   What environment do I need?

2. WORKDIR
   Where will my application live?

3. COPY
   Which files do I need?

4. RUN
   What must be installed/prepared?

5. EXPOSE
   Which port does my application use?

6. ENV
   What configuration does it need?

7. CMD
   How should the application start?
```

This mental model is extremely useful.

# 29. Interview Questions & Answers

## Q1. What is a Dockerfile?

**Answer:**

A Dockerfile is a text file containing instructions used by Docker to build a Docker image.

---

## Q2. Why do we use Dockerfiles?

**Answer:**

Dockerfiles allow us to define the application environment and build process in a repeatable way.

---

## Q3. What is FROM?

**Answer:**

`FROM` specifies the base image from which the Docker image is built.

Example:

```dockerfile
FROM python:3.12
```

---

## Q4. What is WORKDIR?

**Answer:**

`WORKDIR` sets the working directory inside the image for subsequent instructions.

Example:

```dockerfile
WORKDIR /app
```

---

## Q5. What is COPY?

**Answer:**

`COPY` copies files or directories from the build context into the Docker image.

Example:

```dockerfile
COPY . .
```

---

## Q6. What is RUN?

**Answer:**

`RUN` executes commands while building the Docker image.

Example:

```dockerfile
RUN pip install -r requirements.txt
```

---

## Q7. What is CMD?

**Answer:**

`CMD` specifies the default command that runs when a container starts.

Example:

```dockerfile
CMD ["python", "app.py"]
```

---

## Q8. What is the difference between RUN and CMD?

**Answer:**

`RUN` executes during image building, while `CMD` specifies the default command to execute when a container starts.

Short answer:

```text
RUN → Build time
CMD → Container runtime
```

---

## Q9. What is EXPOSE?

**Answer:**

`EXPOSE` documents the port that the application is intended to listen on inside the container.

It does not itself publish the port to the host.

---

## Q10. Does EXPOSE publish a port?

**Answer:**

No.

For example:

```dockerfile
EXPOSE 8000
```

doesn't automatically make the application available on the host.

We can publish it using:

```bash
docker run -p 8000:8000 my-app
```

---

## Q11. What is ENV?

**Answer:**

`ENV` sets environment variables inside the image/container.

Example:

```dockerfile
ENV APP_ENV=production
```

---

## Q12. Can a Dockerfile have multiple CMD instructions?

**Answer:**

A Dockerfile can contain multiple `CMD` instructions, but only the last one takes effect.

In practice, we normally use one `CMD`.

---

## Q13. What happens when we run docker build?

**Answer:**

Docker reads the Dockerfile instructions and builds a Docker image according to those instructions.

---

## Q14. What is the difference between Dockerfile and Docker image?

**Answer:**

A Dockerfile contains instructions for building an image, while an image is the packaged result that can be used to create containers.

---

## Q15. What is the difference between image and container?

**Answer:**

An image is a packaged template, while a container is a running or created instance of that image.

# 🎯 Key Takeaways

- Dockerfile is used to build Docker images.
- `FROM` selects the base image.
- `WORKDIR` sets the working directory.
- `COPY` copies application files.
- `RUN` executes commands during image building.
- `CMD` defines the default startup command.
- `EXPOSE` documents the container's intended port.
- `ENV` defines environment variables.
- `docker build` creates an image.
- `docker run` creates and starts a container.
- `RUN` and `CMD` are NOT the same.
- `EXPOSE` and `-p` are NOT the same.
